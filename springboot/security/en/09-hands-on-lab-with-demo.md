# 09 — Hands-on lab with the demo

Every part follows the same loop: **send a request → observe the result → compare with the code → explain it with the theory**.
Sample output comes from Spring Boot 4.1.2, Spring Security 7.1.2, JDK 21. Your token and session id values will differ.
The demo's response messages are in unaccented Vietnamese; see the translation table in the [README](README.md#the-demos-messages-are-in-vietnamese).

## Setup

Use two terminals.

**T1** runs the application with DEBUG logging:

```bash
cd springboot/security/demo
mvn spring-boot:run -Dspring-boot.run.arguments=--logging.level.org.springframework.security=DEBUG
```

Wait for the line `Started SecurityDemoApplication`. Scroll up to find the two `Will secure ...` lines: those are the
filter lists of the two chains (explained in [lesson 2](02-filter-chain-architecture.md)).

**T2** sends requests:

```bash
B=http://localhost:8088
```

Built-in users: `user` / `password` (USER), `admin` / `admin123` (USER, ADMIN).

Endpoint map:

| Endpoint | Chain | Requires |
|----------|-------|----------|
| `GET /` | Web | Public |
| `GET /web/home` | Web | Login |
| `POST /web/profile/display-name` | Web | Login + CSRF token |
| `POST /api/auth/login` | API | Public |
| `GET /api/public/hello` | API | Public |
| `GET /api/me` | API | A valid token |
| `GET /api/admin/stats` | API | Role ADMIN |
| `GET /api/notes/{id}` | API | The note's owner or ADMIN |
| `DELETE /api/notes/{id}` | API | Role ADMIN |

## Part A — Form login, session and CSRF

Code: [WebSecurityConfig.java](../demo/src/main/java/demo/security/config/WebSecurityConfig.java)

### A1. A public page and a protected page

```bash
curl -i $B/
curl -i -c cookies.txt $B/web/home
```

```
HTTP/1.1 200
Trang chu cong khai. Thu vao /web/home de bi chuyen sang /login.

HTTP/1.1 302
Set-Cookie: JSESSIONID=AD68BE146C4700E87F39046E300D5C76; Path=/; HttpOnly
Location: http://localhost:8088/login
```

Explanation: `/` matches `permitAll()`. `/web/home` falls into `anyRequest().authenticated()`; the user is anonymous,
so `ExceptionTranslationFilter` calls the form-login entry point: a redirect to `/login`. A session is created to
remember the URL you were heading for.

`-c cookies.txt` saves received cookies; `-b cookies.txt` sends the saved ones. These two flags play the browser.

### A2. Get the CSRF token from the login page

```bash
CSRF=$(curl -s -b cookies.txt -c cookies.txt $B/login \
       | sed -nE 's/.*name="_csrf" type="hidden" value="([^"]+)".*/\1/p')
echo $CSRF
```

The login page generated by Spring already contains `<input name="_csrf" type="hidden" value="...">`. Run the command
twice and you get two different values within the same session: the token is masked with a random value on each render.

### A3. Log in without a CSRF token, then with a wrong password

```bash
curl -i -b cookies.txt -X POST $B/login -d "username=user&password=password"
```

```
HTTP/1.1 403
```

The password is correct and it is still 403. In T1:

```
CsrfFilter : Invalid CSRF token found for http://localhost:8088/login
```

`CsrfFilter` comes before `UsernamePasswordAuthenticationFilter`, so the request is stopped before the password is even looked at.

```bash
curl -i -b cookies.txt -c cookies.txt -X POST $B/login \
     --data-urlencode "username=user" --data-urlencode "password=sai" --data-urlencode "_csrf=$CSRF"
```

```
HTTP/1.1 302
Location: http://localhost:8088/login?error
```

### A4. Log in correctly

```bash
curl -i -b cookies.txt -c cookies.txt -X POST $B/login \
     --data-urlencode "username=user" --data-urlencode "password=password" --data-urlencode "_csrf=$CSRF"
```

```
HTTP/1.1 302
Set-Cookie: JSESSIONID=EBCB28D51CFA106F111EAE0C530E71C5; Path=/; HttpOnly
Location: http://localhost:8088/web/home?continue
```

Two things to notice:

- `JSESSIONID` **changed** compared with A1: session fixation protection.
- `Location` is `/web/home`, the page you originally wanted, not `/`: Spring saved the original request.

```bash
curl -b cookies.txt $B/web/home
# Xin chao user, ban dang dung session cookie.
```

The server recognises you by the cookie alone. Delete `cookies.txt` and you are "logged out".

### A5. CSRF on a write request

```bash
curl -i -b cookies.txt -X POST $B/web/profile/display-name -d 'value=An'
# HTTP/1.1 403
```

Logged in, still 403: this is exactly the request a malicious page could make your browser send.

Get a fresh token and retry. The token from A2 no longer works because Spring **replaces the CSRF token after login**
(log: `CsrfAuthenticationStrategy : Replaced CSRF Token`). The logout confirmation page `GET /logout` carries the new one:

```bash
CSRF=$(curl -s -b cookies.txt $B/logout \
       | sed -nE 's/.*name="_csrf" type="hidden" value="([^"]+)".*/\1/p')

curl -i -b cookies.txt -X POST $B/web/profile/display-name \
     --data-urlencode 'value=An' --data-urlencode "_csrf=$CSRF"
```

```
HTTP/1.1 200
Da doi ten hien thi cua user thanh: An
```

The token can also be sent in a header (what SPAs usually do):

```bash
curl -i -b cookies.txt -X POST $B/web/profile/display-name \
     -H "X-CSRF-TOKEN: $CSRF" --data-urlencode 'value=Binh'
# HTTP/1.1 200
```

### A6. Security headers

```bash
curl -s -i -b cookies.txt $B/web/home | grep -E '^(X-|Cache|Pragma|Expires)'
```

```
X-Content-Type-Options: nosniff
X-XSS-Protection: 0
Cache-Control: no-cache, no-store, max-age=0, must-revalidate
Pragma: no-cache
Expires: 0
X-Frame-Options: DENY
```

No line of the demo's configuration produces them: `HeaderWriterFilter` is on by default. The meaning of each header
is in [lesson 5](05-csrf-cors-session-and-headers.md#4-security-headers).

### A7. The two chains do not share an authentication mechanism

```bash
curl -i -b cookies.txt $B/api/me
# HTTP/1.1 401
```

You are logged in on the web side, yet `/api/me` returns 401. The request matches `securityMatcher("/api/**")` and
goes to the API chain; that chain is `STATELESS`, does not read the session, and only accepts bearer tokens.

The other way round, HTTP Basic is not enabled on the web chain:

```bash
curl -i -u user:password $B/web/home
# HTTP/1.1 302   (redirected to /login)
```

### A8. Log out

```bash
curl -i -b cookies.txt -c cookies.txt -X POST $B/logout --data-urlencode "_csrf=$CSRF"
curl -i -b cookies.txt $B/web/home
```

```
HTTP/1.1 302
Location: http://localhost:8088/login?logout

HTTP/1.1 302
Location: http://localhost:8088/login
```

The session is destroyed on the server. The old cookie, even if still in the file, is meaningless: this is the
"instantly revocable" advantage of sessions.

## Part B — REST API with JWT

Code: [ApiSecurityConfig.java](../demo/src/main/java/demo/security/config/ApiSecurityConfig.java),
[JwtConfig.java](../demo/src/main/java/demo/security/config/JwtConfig.java),
[AuthController.java](../demo/src/main/java/demo/security/auth/AuthController.java)

### B1. Public and 401

```bash
curl -i $B/api/public/hello
curl -i $B/api/me
```

```
HTTP/1.1 200
{"message":"Xin chao, endpoint nay ai cung goi duoc"}

HTTP/1.1 401
WWW-Authenticate: Bearer
Content-Type: application/json;charset=UTF-8

{"status":401,"error":"Unauthorized","message":"Chua xac thuc hoac token khong hop le"}
```

Both are "not logged in", but the web chain answers 302 and the API chain answers a JSON 401: the difference is the
`AuthenticationEntryPoint` ([JsonSecurityErrorHandlers.java](../demo/src/main/java/demo/security/error/JsonSecurityErrorHandlers.java)).

The T1 log for `/api/me`:

```
FilterChainProxy              : Securing GET /api/me
AnonymousAuthenticationFilter : Set SecurityContextHolder to anonymous SecurityContext
```

No `Secured` line: the request stopped inside the chain.

A URL that does not exist also returns 401 rather than 404:

```bash
curl -s -o /dev/null -w '%{http_code}\n' $B/api/khong-ton-tai
# 401
```

Security runs before the controller lookup. That is good: outsiders cannot probe which endpoints exist.

### B2. Wrong and correct login

```bash
curl -i -X POST $B/api/auth/login -H 'Content-Type: application/json' \
     -d '{"username":"user","password":"x"}'
# HTTP/1.1 401
```

```
DaoAuthenticationProvider : Failed to authenticate since password does not match stored value
ProviderManager           : Authentication failed with provider DaoAuthenticationProvider since Bad credentials
```

This request needs no CSRF token: the API chain turned CSRF off because it does not use cookies.

```bash
curl -s -X POST $B/api/auth/login -H 'Content-Type: application/json' \
     -d '{"username":"user","password":"password"}'
```

```json
{"accessToken":"eyJhbGciOiJIUzI1NiJ9.eyJpc3MiOi...","tokenType":"Bearer","expiresIn":900}
```

Save the token in a variable:

```bash
TOKEN=$(curl -s -X POST $B/api/auth/login -H 'Content-Type: application/json' \
        -d '{"username":"user","password":"password"}' \
        | sed -E 's/.*"accessToken":"([^"]+)".*/\1/')
```

### B3. Dissect the token

```bash
echo $TOKEN | cut -d. -f1 | base64 -d; echo
echo $TOKEN | cut -d. -f2 | base64 -d; echo
```

```
{"alg":"HS256"}
{"iss":"spring-security-study-demo","sub":"user","exp":1795709569,"iat":1795708669,"roles":["ROLE_USER"]}
```

No secret is needed to read it. If `base64 -d` complains about the length, append one or two `=` characters, or paste
the token into jwt.io (demo tokens only; never paste a production token into an external website).

Compare with [TokenService.java](../demo/src/main/java/demo/security/auth/TokenService.java): each claim corresponds to one line of `JwtClaimsSet.builder()`.

### B4. Call the API with the token

```bash
curl -s $B/api/me -H "Authorization: Bearer $TOKEN"
```

```json
{"authorities":["FACTOR_BEARER","ROLE_USER"],"username":"user","tokenExpiresAt":"2026-11-26T16:12:49Z"}
```

```
JwtAuthenticationProvider       : Authenticated token
BearerTokenAuthenticationFilter : Set SecurityContextHolder to JwtAuthenticationToken [...
                                  Details=WebAuthenticationDetails [RemoteIpAddress=0:0:0:0:0:0:0:1, SessionId=null],
                                  Granted Authorities=[FactorGrantedAuthority [authority=FACTOR_BEARER, ...], ROLE_USER]]
FilterChainProxy                : Secured GET /api/me
```

`SessionId=null`: there is no session. Every request proves its identity on its own.

Without the `Bearer` prefix the token is not recognised:

```bash
curl -s -o /dev/null -w '%{http_code}\n' $B/api/me -H "Authorization: $TOKEN"
# 401
```

### B5. Tamper with the token

```bash
curl -i $B/api/me -H "Authorization: Bearer ${TOKEN}x"
# HTTP/1.1 401
```

```
ProviderManager : Authentication failed with provider JwtAuthenticationProvider since
                  An error occurred while attempting to decode the Jwt: Signed JWT rejected: Invalid signature
```

The response to the client stays generic; the detailed reason is only in the server log. That is deliberate.

### B6. 403: authorization by URL

```bash
curl -i $B/api/admin/stats -H "Authorization: Bearer $TOKEN"
```

```
HTTP/1.1 403
{"status":403,"error":"Forbidden","message":"Khong du quyen truy cap tai nguyen nay"}
```

The token is valid (authenticated), but the rule `requestMatchers("/api/admin/**").hasRole("ADMIN")` denies. Compare
with B1: no token is 401, a token without the permission is 403.

With an admin token:

```bash
ADMIN=$(curl -s -X POST $B/api/auth/login -H 'Content-Type: application/json' \
        -d '{"username":"admin","password":"admin123"}' \
        | sed -E 's/.*"accessToken":"([^"]+)".*/\1/')

curl -s $B/api/admin/stats -H "Authorization: Bearer $ADMIN"
# {"totalUsers":2,"note":"Chi ADMIN thay duoc"}
```

## Part C — Method security: data-level permissions

Code: [NoteService.java](../demo/src/main/java/demo/security/api/NoteService.java)

Note 1 belongs to `user`, note 2 belongs to `admin`.

```bash
curl -s $B/api/notes/1 -H "Authorization: Bearer $TOKEN"
# {"id":1,"owner":"user","content":"Ghi chu rieng cua user"}

curl -i $B/api/notes/2 -H "Authorization: Bearer $TOKEN"
# HTTP/1.1 403
```

Same URL pattern, same user, same URL rule (`authenticated()`), different results because the data differs. The log:

```
FilterChainProxy : Secured GET /api/notes/2
AuthorizationManagerAfterMethodInterceptor : Failed to authorize ... NoteService.findById(long) ...
   ExpressionAuthorizationDecision [granted=false,
   expressionAttribute=returnObject.owner == authentication.name or hasRole('ADMIN')]
```

This time there **is** a `Secured` line: the request passed the filter chain, reached the controller, and was denied
at the service layer.

```bash
curl -s $B/api/notes/1 -H "Authorization: Bearer $ADMIN"                              # 200: ADMIN reads any note
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE $B/api/notes/1 -H "Authorization: Bearer $TOKEN"   # 403
curl -s -o /dev/null -w '%{http_code}\n' -X DELETE $B/api/notes/2 -H "Authorization: Bearer $ADMIN"   # 204
curl -s -o /dev/null -w '%{http_code}\n' $B/api/notes/99 -H "Authorization: Bearer $TOKEN"            # 404
```

## Part D — CORS preflight

```bash
curl -i -X OPTIONS $B/api/me \
     -H 'Origin: https://app.example.com' -H 'Access-Control-Request-Method: GET'
# HTTP/1.1 401
```

The demo has no CORS configuration. A preflight carries no token, so it is blocked like any anonymous request; a
browser would report a CORS error and never send the real request. Fix it in exercise 5 below.

## Exercises

After each change: run `mvn test` to see which tests go red and why, then try again with `curl`.

| # | Task | What you learn |
|---|------|----------------|
| 1 | In `ApiSecurityConfig`, move the `anyRequest().authenticated()` line to the top | The application does not start. Read the error message |
| 2 | Remove `@EnableMethodSecurity`, then let `user` read note 2 | The annotations are still there but protect nothing. Which test catches it? |
| 3 | In `JwtConfig`, drop the `setAuthorityPrefix("")` line. Call `/api/me` and `/api/admin/stats` with an admin token | The authority becomes `SCOPE_ROLE_ADMIN`; even the admin gets 403 |
| 4 | Remove `.csrf(csrf -> csrf.disable())` from the API chain and try to log in through the API | `POST /api/auth/login` returns 403. Understand why a stateless API turns CSRF off |
| 5 | Add a `CorsConfigurationSource` bean for `https://app.example.com` and `http.cors(Customizer.withDefaults())` to the API chain. Rerun part D | The preflight returns 200 with `Access-Control-Allow-Origin` |
| 6 | Set `app.jwt.ttl-minutes: 1`, get a token, wait about two minutes, then call `/api/me` | 401 because it expired. The decoder tolerates 60 seconds of clock skew, so it does not expire exactly at the first minute |
| 7 | Add a `STAFF` role, a `staff` user, and a `/api/reports` endpoint for `hasAnyRole("ADMIN", "STAFF")`. Write tests for all three users | Writing a complete rule with its tests |
| 8 | Add `PUT /api/notes/{id}` for the note's owner only, using `@PreAuthorize` with a checking bean | Data-level authorization for a write operation |
| 9 | Replace `InMemoryUserDetailsManager` with a `UserDetailsService` reading from a database (H2 + Spring Data JPA) | Wiring a real user source, following the pattern in [lesson 3](03-authentication.md#from-a-database-real-projects) |

Finishing exercises 7, 8 and 9 means you can build the basic security of a real project yourself.
Before going to production, walk through the [checklist in lesson 8](08-testing-debugging-and-troubleshooting.md#4-production-checklist).
